# 认证和鉴权是一回事吗？

不是。这是两个独立步骤，顺序也不能颠倒：

| 概念 | 英文 | 回答的问题 | 典型场景 |
| --- | --- | --- | --- |
| **认证** | Authentication | 你是谁？ | 登录、验 token、校验 API Key |
| **鉴权** | Authorization | 你能做什么？ | 普通用户不能删文章、管理员才能进后台 |

可以把它理解成进写字楼的流程：

1. **认证** — 前台核对工牌，确认你的身份
2. **鉴权** — 刷卡进机房，确认你有权限进入这一层

认证失败返回 `401 Unauthorized`（未登录或凭证无效）；鉴权失败返回 `403 Forbidden`（已登录，但没有权限）。

# 认证：常见方案

## Session + Cookie

最经典的服务端会话模型。用户登录成功后，服务端创建 session 并存入 Redis / 数据库，把 session ID 写入 Cookie 返回给浏览器。后续请求自动携带 Cookie，服务端查 session 确认身份。

```
浏览器                    服务端                    存储
  │── POST /login ────────>│
  │   { email, password }  │── 校验密码
  │                        │── 创建 session ────────> Redis
  │<── Set-Cookie: sid ────│
  │                        │
  │── GET /profile ───────>│
  │   Cookie: sid=abc      │── 查 session ─────────> Redis
  │<── 200 { name: ... } ──│
```

**优点**：服务端可随时吊销 session（改密码、踢下线）；Cookie 可设 `HttpOnly`，防 XSS 窃取。

**缺点**：需要共享存储（多实例部署时 session 要集中管理）；Cookie 跨域配置较繁琐。

适合传统 Web 应用、同域前后端一体项目。

## JWT（JSON Web Token）

无状态方案。登录成功后服务端签发 JWT，客户端保存在 localStorage 或 Cookie 里，每次请求在 `Authorization: Bearer <token>` 里带上。

很多人以为 JWT 是加密的，别人看不到里面的内容。不是。前两段只做了 Base64 编码，任何人拿到 token 都能解码看到里面的数据。

签名的作用不是"让别人看不到"，而是"让别人改不了"。服务端收到 token 后，用自己保管的 secret 重新算一遍签名，跟 token 里带的签名对不上，说明数据被动过手脚，直接拒绝。

所以：不要往 JWT 的 payload 里放密码、手机号这些敏感信息。 放用户 ID、角色这些"被别人看到也无所谓"的东西就好。

JWT 由三部分组成，用 `.` 连接：

```
Header.Payload.Signature
```

- **Header** — 算法信息（如 HS256）
- **Payload** — 用户 ID、角色、过期时间等 claims
- **Signature** — 用密钥对前两部分签名，防篡改

# 用 Hono 内置 JWT 中间件做认证

Hono 自带了 JWT 中间件，直接用：

```js
import { Hono } from 'hono'
import { jwt } from 'hono/jwt'
import type { JwtVariables } from 'hono/jwt'

type Variables = JwtVariables

const app = new Hono<{ Variables: Variables }>()

// 公开路由
app.get('/', (c) => {
  return c.text('Public homepage')
})

// /api 下的所有路由都需要 JWT 认证
app.use('/api/*', jwt({ secret: 'my-secret', alg: 'HS256' }))

// 认证通过后，从 jwtPayload 拿到用户信息
app.get('/api/profile', (c) => {
  const payload = c.get('jwtPayload')
  return c.json({
    userId: payload.sub,
    email: payload.email,
  })
})

app.get('/api/orders', (c) => {
  const payload = c.get('jwtPayload')
  return c.json({
    message: `Fetching orders for user ${payload.sub}`,
  })
})

export default app
```

jwt() 中间件做了这几件事：

从 `Authorization: Bearer <token>` 头里取出 token
用 secret 验证签名是否合法
把解码后的 payload 存到 c.set('jwtPayload', ...)
验证失败自动返回 401
你不需要自己写解析逻辑，一行 jwt({ secret }) 搞定。

这里有两个新手容易混淆的点：

secret 是服务端自己保管的密钥，不会发给前端
jwtPayload 不是原始 token，而是 token 解码并验签通过后的内容
也就是说，前端传来的是一整串 token，Hono 帮你验证后，才把里面的数据放到 c.get('jwtPayload') 里。

# 签发JWT
光校验不行，还得能签发 token。用 hono/jwt 的 sign 方法：


```js
import { Hono } from 'hono'
import { jwt, sign } from 'hono/jwt'
import type { JwtVariables } from 'hono/jwt'

type Variables = JwtVariables

const app = new Hono<{ Variables: Variables }>()

// 模拟用户数据
const users = [
  { id: 1, email: 'alice@example.com', password: '123456', role: 'admin' },
  { id: 2, email: 'bob@example.com', password: 'abcdef', role: 'user' },
]

const SECRET = 'my-secret'

// 登录接口：验证用户，签发 token
app.post('/login', async (c) => {
  const { email, password } = await c.req.json()

  const user = users.find(
    (u) => u.email === email && u.password === password
  )

  if (!user) {
    return c.json({ error: 'Invalid credentials' }, 401)
  }

  // 签发 JWT
  const token = await sign(
    {
      sub: user.id,
      email: user.email,
      role: user.role,
      exp: Math.floor(Date.now() / 1000) + 60 * 60 * 24, // 24 小时过期
    },
    SECRET
  )

  return c.json({ token })
})

// 受保护的路由
app.use('/api/*', jwt({ secret: SECRET, alg: 'HS256' }))

app.get('/api/profile', (c) => {
  const payload = c.get('jwtPayload')
  return c.json(payload)
})

export default app
```

sign() 接两个参数：payload 对象和 secret。payload 里的 sub 是标准字段，表示用户 ID；exp 是过期时间，Unix 时间戳。

登录接口负责"验证用户名密码是否正确"
sign() 负责"把用户身份打包成 token"
后续受保护接口负责"验证这个 token 还可信不可信"

## Refresh Token

session：一次登录状态
access token：拿来访问接口的短期凭证
refresh token：拿来续 access token 的长期凭证

refresh token 不是拿来频繁访问业务接口的。

它的作用只有一个：

当 access token 过期之后，用它去换一个新的 access token。

这就像你的 access token 是门禁卡，过一会儿就失效；refresh token 更像服务台的续卡凭证。

所以 refresh token 和 access token 的差别不是“小一点、大一点”这种区别，而是职责完全不同：

access token：负责访问接口
refresh token：负责续 access token
它通常会活得更久，比如 7 天、14 天、30 天。

但也正因为它活得久，所以它更敏感，服务端必须更严格地管理它。

refresh token 必须落库，而且通常只存 hash，不存明文。

这样服务端才能知道：

它有没有过期
它有没有被使用过
它有没有被撤销
它是不是已经被新的 token 替换掉了

# refresh token rotation
既然 refresh token 活得久，那它一旦泄漏，风险天然就更高。

如果同一个 refresh token 可以被反复使用很多次，那攻击者只要拿到一次，就能长期续命。

所以更安全的方案是：

每次刷新都让旧 refresh token 失效
同时签发一个新的 refresh token
这就叫 refresh token rotation。

这样做的好处很直接：

旧 token 被偷后，价值会迅速下降
服务端更容易发现重复使用
同一个 session 的续期链路更可控

**推荐 access token 放内存，refresh token 放 cookie**




## 完整的链路

真正的客户端 token 流程，通常是下面这样：

1. 用户登录成功
2. 服务端创建一条 session
3. 服务端签发一个短效 access token
4. 服务端签发一个长效 refresh token
5. access token 用来访问业务接口
6. access token 过期后，用 refresh token 去换新的 access token
7. refresh token 每次刷新都轮换

所以真正的顺序不是：

先有 token
而是：

先有 session
再有围绕 session 生成出来的 token


## OAuth 2.0 / OpenID Connect

第三方登录的标准协议。「用 GitHub / Google / 微信登录」走的就是 OAuth。

```
用户 ──> 你的应用 ──> 重定向到 GitHub ──> 用户授权
                                              │
用户 <── 你的应用 <── 回调带 code <───────────┘
         │
         └── 用 code 换 access_token ──> GitHub API 获取用户信息
```

OAuth 解决的是「如何安全地让第三方应用访问用户在其他平台的数据」，OpenID Connect（OIDC）在 OAuth 之上加了身份层，返回 ID Token 表明用户身份。

## API Key

最简单的机器间认证。服务端生成密钥，客户端在请求头里携带：

```
Authorization: Bearer sk_live_xxxxxxxx
```

适合服务端调用、Webhook、内部工具。密钥应可轮换、可按 scope 限制权限，不要硬编码在前端代码里。

# 鉴权：常见模型

## RBAC（基于角色）

给每个用户分配角色，角色绑定权限集合：

```
用户 ──> 角色 ──> 权限
alice ──> editor ──> [post:write, post:read]
bob  ──> admin  ──> [post:write, post:read, post:delete, user:manage]
```

实现简单，适合权限层级清晰的系统（后台管理、CMS）。

## ABAC（基于属性）

根据用户属性、资源属性、环境上下文动态判断：

```
允许删除，当：
  user.department == resource.department
  AND user.level >= 3
  AND time.hour 在 9:00-18:00 之间
```

更灵活，但规则复杂，一般大型系统或合规场景才需要。

## 资源所有权

最常见的细粒度控制：用户只能操作自己创建的资源。

```js
// 伪代码
async function deletePost(userId, postId) {
  const post = await db.query.posts.findFirst({ where: eq(posts.id, postId) })

  if (!post) throw new NotFoundError()
  if (post.authorId !== userId && !user.isAdmin) throw new ForbiddenError()

  await db.delete(posts).where(eq(posts.id, postId))
}
```

# 实战：Hono 中间件分层

以 Hono（Cloudflare Workers 常用框架）为例，认证和鉴权应拆成独立中间件，职责清晰：

```js
// middleware/auth.js — 认证：解析 token，挂载 user 到 context
export const authMiddleware = createMiddleware(async (c, next) => {
  const token = c.req.header('Authorization')?.replace('Bearer ', '')

  if (!token) {
    return c.json({ error: 'Unauthorized' }, 401)
  }

  try {
    const payload = await verify(token, c.env.JWT_SECRET)
    const user = await db.query.users.findFirst({
      where: eq(users.id, payload.sub),
    })

    if (!user) {
      return c.json({ error: 'Unauthorized' }, 401)
    }

    c.set('user', user)
    await next()
  } catch {
    return c.json({ error: 'Invalid token' }, 401)
  }
})

// middleware/rbac.js — 鉴权：检查角色
export const requireRole = (...roles) =>
  createMiddleware(async (c, next) => {
    const user = c.get('user')

    if (!roles.includes(user.role)) {
      return c.json({ error: 'Forbidden' }, 403)
    }

    await next()
  })
```

路由层组合使用：

```js
// 公开接口 — 不需要认证
app.get('/posts', listPosts)

// 需要登录 — 只过 authMiddleware
app.post('/posts', authMiddleware, createPost)

// 需要管理员 — auth + 角色校验
app.delete('/posts/:id', authMiddleware, requireRole('admin'), deletePost)

// 需要登录 + 资源所有权 — auth + 业务层校验
app.put('/posts/:id', authMiddleware, updateOwnPost)
```

请求链路：

```
Request
  │
  ▼
authMiddleware ── 401 ──> 结束
  │ 通过，c.set('user', ...)
  ▼
requireRole('admin') ── 403 ──> 结束
  │ 通过
  ▼
deletePost handler ── 404/200 ──> 结束
```

# 前端侧要注意什么

## Token 存哪里

| 存储方式 | 安全考量 |
| --- | --- |
| HttpOnly Cookie | 防 XSS 读取，推荐用于 session / refresh token |
| localStorage | 任何 JS 都能读，XSS 即泄露，JWT 存这里风险较高 |
| memory（内存变量） | 最安全，但刷新页面丢失，需配合 silent refresh |

## 请求拦截

无论用 fetch 还是 axios / TanStack Query，统一在请求层附加凭证：

```js
// fetch 封装
async function api(path, options = {}) {
  const token = getAccessToken()

  return fetch(path, {
    ...options,
    headers: {
      ...options.headers,
      ...(token && { Authorization: `Bearer ${token}` }),
    },
  })
}
```

## 401 / 403 的处理

- **401** — token 过期或无效，尝试 refresh；refresh 也失败则跳转登录页
- **403** — 权限不足，提示用户或隐藏无权限的操作入口（更好的做法是在 UI 层就不展示）

不要在每个组件里各自处理，统一放在 HTTP client 或路由 guard 里。

# 安全清单

**密码**

- 用 bcrypt / argon2 哈希存储，绝不存明文
- 登录接口加 rate limit，防暴力破解

**Token**

- Access Token 短过期（≤ 1h）
- Refresh Token 存 HttpOnly Cookie，`SameSite=Strict`
- 密钥放环境变量，不要提交到 Git

**传输**

- 全站 HTTPS
- Cookie 设 `Secure` 标志

**CORS**

- 不要用 `Access-Control-Allow-Origin: *` 配合 credentials
- 白名单指定允许的 origin

**最小权限**

- API Key / JWT claims 只给必要的 scope
- 后台接口和管理员操作单独路由、单独鉴权

# 常见误区

**把鉴权逻辑写在前端**

前端隐藏按钮只是 UX，不能替代服务端鉴权。所有权限判断必须在 API 层执行。

**JWT 里塞太多数据**

Payload 会随每个请求传输，放 userId + role 足够，详细用户信息查库。

**401 和 403 混用**

已登录但权限不够，应返回 403 而非 401。前端依赖这个状态码做不同处理。

**OAuth 回调不校验 state**

state 参数防 CSRF，发起授权时必须生成随机 state 并在回调时校验。

**Session 不设过期**

无论 session 还是 JWT，都必须有过期机制。长期有效的凭证 = 长期有效的攻击窗口。

# 怎么选方案

| 场景 | 推荐方案 |
| --- | --- |
| 同域 Web 应用 | Session + HttpOnly Cookie |
| SPA + 独立 API | JWT + Refresh Token |
| 移动端 App | JWT 或 OAuth Device Flow |
| 第三方集成 / 开放平台 | OAuth 2.0 + API Key |
| 微服务内部调用 | mTLS 或 Service Account JWT |
| Cloudflare Workers 边缘 API | JWT（无状态，适合边缘无共享存储） |

没有银弹。选方案时优先考虑：是否需要主动吊销、部署架构是否多实例、客户端类型（浏览器 / App / 服务端）、以及团队对复杂度的承受能力。

认证解决「身份可信」，鉴权解决「操作合法」。先把这两层边界划清楚，再选具体技术方案，后面的代码会好写很多。
